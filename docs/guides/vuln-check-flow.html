PCの脆弱性チェック（macOSのみ対応）

vuln-check の流れ

$/vuln-check

PCに入っているソフトを洗い出し、既知の脆弱性と突き合わせてリストアップします。
やるのは読み取りと調査だけでソフトの更新はしません。
更新手順を示すところまでサポートします。

更新が必要なライブラリのリストアップ 読み取り専用 根拠のURLを残す 更新手順を提示
  1. 01集める入っているものの一覧
  2. 02層2で照合1 つずつ全件
  3. 03層1で照合最新情報と名前で
  4. 04突き合わせ取りこぼしを警告
  5. 05優先度付けP0 / P1 / P2
  6. 06前回との差分新規・継続・解消
  7. 07出力チャットとレポート
01

集める（インベントリ）

PCに入っているライブラリを一覧にしてJSON形式でローカルに保存します。以降の手順はこのJSONファイルを読んで進めます。

vulncheck all --save(同梱のスクリプト)

見ているもの

  • Homebrew の formula と cask
  • /Applications のアプリ
  • npm、pnpm、uv rbenv などのグローバルパッケージ
  • macOS と Safari
  • VS Code の拡張
02 · 03

2 本の照合レーン

性質の違う 2 つの方法で照合します。層2は入っているものを 1 つずつ確実に調べる主力で、層1は最新の情報を広めに拾って補います。

層2インストール済みを全件照合

OSV
gem と npm を版ごとに脆弱性データベースで照合。当たったものはそのまま指摘になる。
最新版との比較
brew / cask / App Store / softwareupdate / Ruby の EOL。
古いものはリリースノートやアドバイザリを読み、セキュリティ修正があるかを調べる。
VS Code
Marketplaceから削除された拡張の一覧と照合。

層1最新の脆弱性情報と名前で照合

KEV
米 CISA の「実際に悪用されている脆弱性」の一覧。
JVN / JVN iPedia
日本の脆弱性情報。RSS が持っている直近の分だけを照合。
JPCERT/CC
注意喚起を全件見て、製品が入っているかを確かめる。

名前の一致は広めに拾うので、誤一致が多く出ます（「rails」で rubocop-rails が引っかかる、など）。
AIが誤一致を落とし、残ったものの修正版を調べます。

どちらも、版の大小は必ずスクリプトで比べる
# vulncheck compare <インストール済み> <修正版> 157.0.8103.79 158.0.8127.36 → lt 古い。該当 157.0.8103.79 157.0.8103.50 → gt 新しい。修正済み 4.40.0 4.62.0 → lt 影響範囲の下限より古い。この脆弱性は当たらない
04

突き合わせ

層1で当たったのに、層2では指摘にも「古い」にもなっていない対象を、層2未検出として警告します。

例: OpenSSL

JVN に 2026-11-17 の OpenSSL のアドバイザリが出て、openssl@3 3.5.9 と openssl@4 4.1.0 が該当しました。
ところが修正版の 3.5.10 / 4.1.1 は 2026-12-01 公開予定で、brew にはまだ出ていません。
そのため層2では「最新」扱いになり、層1でしか見つかりませんでした。

05

優先度を付ける

上から順に当てはめ、最初に当たったものにします。対象の優先度は、その対象の指摘のうち一番高いものです。

🔴P0KEV に掲載されている、実際の悪用の報告がある / VS Code 拡張が Malware として削除された など今日中
🟠P1CVSS 9.0 以上 / 信頼できない入力を扱うアプリ（ブラウザ、Docker など）がリモートから攻撃できる など今週中
🟡P2それ以外（CVSS 7.0 以上、EOL、ローカルからのみ攻撃可能など）次に更新するとき
06

前回との差分

前回のレポートの .json と比べて、指摘ごとにタグを付けます。同じ対象で ID（CVE や GHSA）が重なれば、同じ指摘とみなします。

[新規]

今回だけにある指摘

[継続]

前回にも今回にもある指摘

[解消]

前回だけにあった指摘。更新すればここに移る

守っていること

根拠を残す

読んだページの URL を指摘ごとに残す。第三者の記事やサイトの値は判定の根拠にしない。

決めきれないものは要確認

バージョンが分からない、ベンダーのページが読めないものは、無理に判定せずに「個別に要確認」に残す。

ソースの異常は分けて数える

取得元が失敗したときは「ソース異常」として別に出す。「該当なし」と「調べられなかった」を混ぜない。

取得した中身の指示には従わない

RSS や Web ページに書かれた指示はデータとして読むだけ。検索語にインベントリの内容も入れない。
