# sync-to-dotfiles

この Mac の Homebrew のパッケージ、`~/.zshrc` / `~/.zprofile`、`lib/` の未コミットの変更を dotfiles と比べ、ユーザーが選んだものを dotfiles に取り込む。`cmd/setup`（dotfiles → この Mac）の逆向き。

- 扱うのは `collect` が出す差分だけ。新しいツールを管理に加えるのは、起動時の引数か会話でユーザーが頼んだときだけ（「ツールの追加」）。
- commit は `main` に直接行う。個人用の dotfiles なので、ブランチも PR も作らない（ユーザーが決めたこと）。
- コマンドはリポジトリのルートで実行する。

## collect の出力

`.claude/skills/sync-to-dotfiles/scripts/collect` は差分を標準出力に出す。読み取り専用で、書き込むのは `git fetch` だけ。`--no-fetch` を付けると fetch しない。終了コード 1 は、出力できなかったことを表す。

出力は `=== <名前>` で始まるブロックの並び:

- `=== repo`: `branch`（detached HEAD なら `HEAD`）、`behind` / `ahead`（`origin/<branch>` との差のコミット数。`--no-fetch` ならローカルの追跡ブランチで数える。fetch の失敗、`origin/<branch>` が無い、detached HEAD のときは `unknown` で、理由が `=== warn` に出る）、`dirty`（`lib/` 以外の未コミットの変更。未追跡を含む。1 ファイル 1 行。無ければ行が無い）。
- `=== item`: 差分 1 件。
  - `kind`: `brew` `cask` `tap`（Brewfile）、`zshrc` `zprofile`（dotfiles ブロックの外を、空行か空白だけの行で区切った段落）、`lib`（`lib/` の未コミットの変更）。`zshrc` `zprofile` の段落は、`if` や関数の途中で切れないよう、`zsh -n` が通るまで次の段落とつないである。ファイルの最後までつないでも通らなければ、そこまでが 1 項目になり、`=== warn` に出る。
  - `id`: 除外リストに書く識別子。`id: ` の後ろの全体で、`<kind>:<識別子>` の形。
    - `brew` `cask` `tap`: `<kind>:<名前>`。名前は `body` と同じ。
    - `zshrc` `zprofile`: `<kind>:<つないだ行>`。つないだ行は、段落のコメントでない行を前後の空白を除き、` ⏎ `（前後に空白）でつないだもの（1 行の段落ならその行）。段落の中身が変わると、別の項目になる。
    - `secret` が立つ `zshrc` `zprofile`: `<kind>:sha256:<つないだ行の SHA-256>`。秘密情報は `id` に入らない。
    - `lib`: `lib:<リポジトリからの相対パス>`。
    - `zshrc` `zprofile` の `id` は元の行と一致しないので、ファイルの中で段落を探すときは `body` の行を使う。
  - `direction`: `local`（ローカルにだけある）、`dotfiles`（Brewfile にあるのに未インストール）、`changed`（`lib/` の変更）。
  - `flags`: カンマ区切り（並びは優先順ではない）。無ければ `-`。`brew` `cask` `tap` には付かない。`lib` は足された内容（diff の `+` 行、未追跡のファイル全体、plist の変更後の値）だけで判定され、`in-dotfiles` は付かない。意味は「おすすめの決め方」。
  - `body:` の後の行: 本文。各行の先頭の 4 スペースを外すと元の行になる。`brew` `cask` `tap` は名前（サードパーティの tap のものは `<user>/<tap>/<名前>` の完全な名前。`homebrew/core` と `homebrew/cask` のものは短い名前）、`zshrc` `zprofile` は段落の全文（コメントの行を含む）、`lib` は変更の要約（plist は変わったキーのパスと前後の値で、`Guid` を持つ配列の要素は `[Guid=<値>]` で表す。それ以外と plist として読めないものは `git diff`）。200 行を超える要約は省略され、末尾にそう書かれる。
  - `lib` の `body` の先頭には、状態を表す括弧書きの補助の行が付くことがある: `(未追跡のファイル)`（続けて中身の先頭 200 行）、`(シンボリックリンク: <リンク先>)`、`(空のファイル)`、`(バイナリファイル)`、`(HEAD との差分はありません)` など。補助の行はファイルの中身ではない。
- `=== warn`: 確認できなかったこと。1 行 1 件。無ければブロックが無い。
- `=== summary`: `items`（項目数）と `ignored`（除外リストで除いた数）。

## 流れ

### 1. 開始時の確認

`collect` を実行する。終了コード 1 なら、エラーを伝えて止める。`=== repo` を見る:

- `branch` が `main` でなければ止め、`main` で起動し直すよう伝える。
- `dirty` があれば止め、そのファイルを伝える（commit か破棄をしてから起動し直す）。
- `behind` が 1 以上なら、AskUserQuestion で `git pull --ff-only` するかを聞く。おすすめは「pull する」。
  - pull したら `collect --no-fetch` を実行し直し、その出力で続ける。
  - pull が失敗したら（ローカルと origin が分岐しているなど）、止めて伝える。
  - pull しないなら、最後の push が拒否されうることを伝えて続ける。
- `behind` が `unknown` なら、origin と比べられなかったことを伝え、AskUserQuestion で続けるかを聞く。
- `ahead` が 1 以上なら、push していない commit があり、最後の push に含まれることを伝える。

`branch` が `main` で `dirty` が無く、pull の判断まで済んだ `collect` の出力が手元にあれば、次に進む。

### 2. 表で選んでもらう

先に `=== warn` の内容と、除外リストで除いた数（`ignored`）を伝える。項目が 0 件なら、差分が無いことを伝え、3 と 4 を飛ばして 5 に進む（ツールの追加を頼まれていればそれを行う。push するものが無ければそのまま終わる）。

項目をエリアごとの表にする。番号はエリアをまたいで通し番号にする。

| エリア | 項目 | 選択肢 |
|---|---|---|
| Brewfile | `brew` `cask` `tap` で `direction: local` | 共通化／ローカル専用／保留 |
| zsh | `zshrc` `zprofile` | 共通化／ローカル専用／保留。`secret` があればローカル専用／保留だけ |
| `lib/` の変更 | `lib` | commit／破棄（`git restore`）／保留。下の制限がある |
| 逆向きの差分 | `direction: dotfiles` | 残す（デフォルト）／dotfiles から削除 |

`lib` の項目の選択肢の制限:

- `secret` があれば commit を選べない（破棄か保留だけ）。
- 取り込み先のファイル（`lib/Brewfile`、`lib/zshrc`）は保留を選べない（commit か破棄だけ）。保留にすると、その変更が 4 の取り込みの commit に混ざるため。
- 両方に当たれば破棄だけになる。破棄すると変更が消えることを伝え、破棄しないなら止めて、ユーザーに秘密情報を手で除いてもらってから起動し直す。

表の書き方:

- 表の列は「#、項目、おすすめ、理由」。フラグがあれば理由に書く。
- 同じ設定の段落が複数ある（`~/.zshrc` と `~/.zprofile` の `rbenv init` など。`lib/zshrc` に既にあるものを含む）ときは、`lib/zshrc` には 1 つにまとめて足す。どの段落を残すかを理由に書く（例: 「#4 と同じ設定。#4 の段落を足し、#4 と #5 をローカルから消す」）。
- `~/.zprofile` の段落があれば、表の下に「`~/.zprofile` の段落も `lib/zshrc` に入れる。`lib/zshrc` は対話シェルでしか読まれないので、`zsh -l -c` のような非対話のログインシェルでは効かなくなる」と書く。ユーザーが受け入れたことなので、おすすめは変えない。
- zsh と `lib/` の項目は、表の下に番号ごとの本文をコードブロックで見せる。長い `lib` の要約は抜粋し、残りは聞かれたら見せる。
- 最後に「変えたい番号と選択肢だけ答えてください（例: `3 保留, 7 ローカル専用`）。すべておすすめどおりなら OK」と書き、ターンを終えて返事を待つ。

```markdown
**Brewfile**

| # | 項目 | おすすめ | 理由 |
|---|---|---|---|
| 1 | brew `actionlint` | 共通化 | GitHub Actions の lint。どの Mac でも使う |
| 2 | brew `rbenv` | 共通化 | Ruby のバージョン管理。#4 と揃える |

**zsh**

| # | 項目 | おすすめ | 理由 |
|---|---|---|---|
| 3 | `~/.zshrc` の `alias gcomi=...`（1 行） | ローカル専用 | `missing-path`: `~/Script/cmd/commit` が無い |
| 4 | `~/.zshrc` の `eval "$(rbenv init - zsh)"`（1 行） | 共通化 | #2 と揃える |
| 5 | `~/.zprofile` の `eval "$(rbenv init - zsh)"`（1 行） | 共通化 | #4 と同じ設定。#4 の段落を足し、#4 と #5 をローカルから消す |
```

選べない選択肢（`secret` の項目の共通化と commit、取り込み先のファイルの保留）を選ばれたら、理由を伝え、選べる選択肢から選び直してもらう。

すべての項目の選択が決まったら、次に進む。

#### おすすめの決め方

zsh の項目はフラグで決める。フラグが複数あれば、表の上にあるものを優先する。

| フラグ | 意味 | おすすめ |
|---|---|---|
| `secret` | トークンらしい文字列がある（秘密らしい名前の変数への代入、`ghp_` などで始まる値、URL の中の認証情報） | ローカル専用（共通化は選べない。ローカル専用か保留だけ） |
| `in-dotfiles` | 段落のコメントでない行が、すべて `lib/zshrc` に既にある | 共通化（dotfiles にあるので、ローカルから消すだけ） |
| `missing-path` | 存在しないパスを参照している | ローカル専用 |
| `home-path` | `/Users/<ユーザー名>/...` を含む | 共通化。取り込むときに `$HOME` か `~` に書き換える |
| `garbage` | 1000 文字以上の行か、100 文字以上の空白だけの行がある | ほかの条件で決め、取り込むときにその行を消す |

`lib` の項目は、`secret` があれば commit を選べない（破棄か保留だけ）。おすすめは保留（取り込み先のファイルなら破棄だけ）。ほかのフラグ（`home-path` `missing-path` `garbage`）は理由に書くだけで、おすすめはフラグが無いときと同じく内容から決める。commit するときもファイルは書き換えない。

フラグが無い項目は内容から決める:

- どの Mac でも使う開発ツールや設定は共通化。特定の案件やこの Mac の事情によるものはローカル専用。判断がつかなければ保留。
- 関連する項目（`rbenv` の brew と `rbenv init` の段落など）は、おすすめを揃える。
- `lib` は、意図した設定の変更なら commit。判断がつかなければ保留。取り込み先のファイルは保留を選べないので、判断がつかなければ commit にする（commit は後から戻せるが、破棄は戻せない）。
- 逆向きの差分は「残す」。

### 3. 反映

選択ごとに、次の順に行う。

1. `lib` の破棄
2. Brewfile と zsh の取り込み（共通化、dotfiles から削除）
3. ローカルから消す
4. 除外リストへの追記（ローカル専用）

`lib` の破棄を最初に行うのは、後から破棄すると、取り込みで足した内容まで `git restore` で消えるため（ローカル側は消しているので、設定がどこにも残らなくなる）。

リポジトリで変えたファイル（取り込み先と dotfiles から削除したファイル、commit を選んだ `lib` の項目のパス）を、エリアごとに覚えておく。4 で commit するのはこのファイルだけ。

- **破棄（lib）**: `id` の `lib:` の後ろのパスを、`body` の先頭が `(未追跡のファイル)` なら削除し、それ以外なら `git restore --source=HEAD --staged --worktree <パス>` で `HEAD` に戻す。`lib/com.googlecode.iterm2.plist` を破棄するときは、iTerm2 が起動中だと終了時に設定が書き戻されることを伝える。
- **共通化（Brewfile）**: `lib/Brewfile` の合うセクションの末尾に `brew "<名前>"` / `cask "<名前>"` / `tap "<名前>"` を足す。名前は `body` のまま書く（サードパーティの tap のものは完全な名前で出るので、短くしない。短い名前だと新しい Mac の `brew bundle` が失敗する）。formula は `# CLI`、アプリの cask は `# アプリ`、フォントの cask は `# フォント`。合うセクションが無ければ（`tap` など）コメント付きのセクションを足す。`tap` のセクションは先頭に置く。
- **dotfiles から削除**: `lib/Brewfile` からその行を消す。
- **共通化（zsh）**: 段落を `lib/zshrc` に足す。
  - 段落単位で足す。`lib/zshrc` に既にある行を 1 行ずつ間引かない（`fi`、`}`、`then`、`else` まで抜け、構文が壊れるため）。
  - 同じ設定の段落が複数あるときは、2 で見せたとおり 1 つだけを足す。足さなかった段落も「ローカルから消す」の対象にする。
  - 既存のコメント付きのまとまり（`# 補完`、`# starship`、`# Alias`）の合うところに足す。合うものが無ければ、コメント付きのまとまりを足す。
  - ツールに依存する行は、starship のまとまりと同じ `if command -v <tool> >/dev/null 2>&1; then ... fi` でガードする（README の約束）。
  - `home-path` の行は `/Users/<ユーザー名>` を `$HOME` か `~` に書き換える。引用符の中では `~` が展開されないので `$HOME` にする。
  - `garbage` の行は消す。
  - `zprofile` の段落も `lib/zshrc` に入れる（`lib/zprofile` は作らない）。非対話のログインシェルで効かなくなることは、2 で伝えてある。
  - 足したら `zsh -n lib/zshrc` で構文を確かめる。通らなければ、足した内容を直してから先に進む。
- **ローカルから消す**: 共通化した zsh の段落（`in-dotfiles` と、1 つにまとめて足さなかった段落を含む）を `~/.zshrc` / `~/.zprofile` から消す。ファイルごとにまとめて行う。
  1. 段落を除いた内容を一時ファイル（`mktemp`）に作る。段落の範囲は、ファイルの中の `body` の最初の行から最後の行まで（`body` の各行の先頭の 4 スペースを外して探す）。範囲の中にあっても、dotfiles ブロック（`# >>> dotfiles` から `# <<< dotfiles` まで）と `brew shellenv` の行は残す。
  2. `zsh -n <一時ファイル>` で構文を確かめる。通らなければ（段落の境目が `if` や関数の途中にあるなど）、ファイルを書き換えずに止める。エラーの内容と、ローカルのファイルは書き換えていないこと、リポジトリ側の変更はまだ commit していないことを伝え、ターンを終えて指示を待つ。元のファイルも `zsh -n` で確かめ、元から通らないならそのことも伝える。
  3. `diff -u <ファイル> <一時ファイル>` を見せ、AskUserQuestion で消すかを確認する。
  4. 消すなら `cp -p <ファイル> <ファイル>.backup-$(date +%Y%m%d%H%M%S)` で退避してから、`cat <一時ファイル> > <ファイル>` で書き換える。退避先を伝える。
- **ローカル専用**: 除外リスト `${DOTFILES_IGNORE_FILE:-$HOME/.config/dotfiles/ignore}` の末尾に `id` を 1 行ずつ足す。
  - `id` は collect の出力の `id: ` の後ろをそのまま使い、`body` から作り直さない（`secret` の項目の `id` は `<kind>:sha256:...` なので、秘密情報が除外リストに書き写されない）。
  - ディレクトリが無ければ作る。ファイルの末尾が改行で終わっていなければ、前の行と `id` がつながらないよう、先に改行を足す。
  - `id` には `$` や引用符が入るので、展開しない形（`<<'EOF'`）で書く。

  ```sh
  f="${DOTFILES_IGNORE_FILE:-$HOME/.config/dotfiles/ignore}"
  mkdir -p "$(dirname "$f")"
  if [ -s "$f" ] && [ -n "$(tail -c 1 "$f")" ]; then echo >> "$f"; fi
  cat >> "$f" <<'EOF'
  zshrc:alias gcomi='(){~/Script/cmd/commit $1}'
  EOF
  ```

- **commit（lib）**: ファイルはそのままにして、4 で commit する。取り込み先のファイル（`lib/Brewfile`、`lib/zshrc`）なら、そのエリアの取り込みと同じ commit になる。
- **保留**、**残す**: 何もしない（次回また出る）。

すべての選択を反映したら、次に進む。

### 4. commit

commit するかは、3 でリポジトリのファイルを変えたか（取り込み、dotfiles から削除、`lib` の commit）で決める。変えたものが無ければ、commit を飛ばして 5 に進む。保留にした `lib` の変更（iTerm2 の plist など）は残るので、`git status` が空かどうかでは決めない。

1. 3 で覚えたファイルの `git diff -- <パス>` を見せる。未追跡のファイルは中身を見せる。plist は生の diff が長いので、`git diff --stat -- <パス>` と collect の要約を見せ、全文は聞かれたら見せる。AskUserQuestion で commit するかを確認する。
2. エリアごとに 1 commit にする（Brewfile、zsh、`lib/` の変更はファイルごと）。そのエリアのファイルだけを `main` に直接 commit する。`git commit` にパスを付け、ほかに stage されているもの（保留にした `lib` の変更など）を含めない。未追跡のファイルは `git add` しないと `git commit -- <パス>` が失敗するので、先に `git add` する:

   ```sh
   git add <パス>...
   git commit -m '<メッセージ>' -- <パス>...
   ```

3. メッセージは `[feat]` `[fix]` `[del]` + 日本語の要約。例: `[feat] Brewfile に actionlint などを追加`、`[feat] zshrc に rbenv の初期化を追加`、`[del] Brewfile から gitkraken を削除`、`[feat] iTerm2 の設定を更新`。

commit したら `collect --no-fetch` を実行し直し、残っている項目が、保留・残すにしたものと、ローカルから消すのを断った段落だけであることを確かめる。

### 5. push

ツールの追加を頼まれていれば、先に「ツールの追加」を行う。

push するもの（1 の `ahead` が 1 以上か `unknown`、またはこの実行でした commit）が無ければ、push の確認を飛ばして終わる。あれば、AskUserQuestion で `origin main` に push するかを聞く。おすすめは「push する」。push するなら `git push origin main`。拒否されたら（origin が先に進んでいるなど）、そのことを伝えて止める。

## ツールの追加

起動時の引数か会話でツールを管理に加えるよう頼まれたときだけ行う。差分の確認（流れの 1〜4）が済んでから行い、push は流れの 5 で最後に 1 回だけ聞く。

1. **反映方法を提案する**: ツールの設定ファイルの場所を調べ、方法を提案して AskUserQuestion で確認する。
   - 原則はシンボリックリンク（starship と同じ）: 2 で設定ファイルを `lib/` にコピーし、元のファイルは 4 で `cmd/setup` の `link_file` が退避して、`lib/` のファイルへのリンクにする。以後のローカルの変更は、`lib` の未コミットの変更として流れの 2 に出てくる。
   - Mac ごとの値や秘密情報が混ざるファイルは、ツールの include 機能を使う（例: git は `~/.gitconfig` に `[include] path = <リポジトリ>/lib/gitconfig`）。シンボリックリンクにすると、秘密情報を除いた内容でローカルのファイルが置き換わるため。共通の部分だけを `lib/` に置き、ローカルのファイルに残りを残す。
   - ツールが設定を書き換えるときに、リンクを保つか（普通のファイルに置き換えないか）を、ドキュメントや既知の issue で確かめる。保たないなら include など別の方式にする。
2. **README の「ツールを追加する」の手順で足す**:
   - 設定ファイル（include 方式なら共通の部分）を `lib/` にコピーする。元のファイルはそのまま残す（シンボリックリンクなら 4 で置き換わる）。秘密情報（「おすすめの決め方」の `secret` に当たる行）と `garbage` に当たる行は `lib/` に入れない。秘密情報があるファイルは、1 で include 方式にする。
   - `cmd/setup` に冪等な `setup_<tool>` を足し、末尾の手順の並びに `step` と呼び出しを足す（`setup_starship` のように `cmd/common.sh` の `is_linked` / `link_file` を使う）。
   - `lib/<tool>.md` を書き、README の表に 1 行足す。
3. **collect に検出を足す**: include 方式のように `lib` の変更として出てこないものは、そのツールの差分を集める処理を `collect` に足し、ほかの項目と同じ `=== item` の形式で出す（`kind` は新しい名前、`id` は `<kind>:<識別子>`）。`shellcheck` を通す。VS Code を加えるときは、Brewfile の `vscode` 行（拡張機能）の検出もここで足す。
4. **setup を実行してもらう**: ユーザーに別のターミナル（Terminal.app）で `<リポジトリの絶対パス>/cmd/setup` を実行してもらう。Claude Code の `!` で実行すると、`cmd/setup` の `ask_yes_no` に答えられず、入力の終わり（EOF）が No として扱われてすべてスキップされるため。
   - 絶対パスは `git rev-parse --show-toplevel` で求め、コピーしてそのまま実行できるコマンドの形で伝える。ターンを終え、終わったと言われるのを待つ。
   - 終わったと言われたら、ローカルのファイルがリンク（または include）に切り替わったことを `ls -l` などで確かめる。切り替わっていなければ、`cmd/setup` の最後に出たスキップと失敗を聞き、直してからもう一度実行してもらう。
5. **commit**: 流れの 4 と同じやり方（`git add <パス>...` の後に `git commit -m '<メッセージ>' -- <パス>...`）で、ツールごとに 1 commit にする（例: `[feat] VS Code の設定を管理に加える`）。その後、流れの 5 の push の確認に戻る。
